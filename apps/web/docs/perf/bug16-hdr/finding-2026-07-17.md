# BUG16 — 10-bit HDR (bt2020/PQ) HEVC exports as washed-out/crushed bt709 SDR, no tonemap

**Status: architectural finding, not fixed.** The correct fix requires touching
sibling-owned files (`services/video-cache/service.ts`, and/or the ingest probe
in `lib/media/normalize-media.ts` + whatever builds `VideoNodeParams` in
scene-builder). A contained fix inside `services/renderer/scene-exporter.ts`
(this task's owned file) is **not possible** for the reason detailed below —
by the time any file in `services/renderer/**` sees a frame, the HDR pixel
data has already been irreversibly flattened to SDR by browser-native color
management running *inside* the mediabunny dependency, upstream of the entire
owned-file surface.

## Repro

- Fixture: `apps/web/e2e/fixtures/w2/hdr_hevc_1280x720_10bit.mp4` — HEVC Main
  10, `yuv420p10le`, `color_primaries=bt2020`, `color_transfer=smpte2084`
  (PQ), `color_space=bt2020nc`, 1280x720, 30fps, 3s (confirmed via `ffprobe`).
- Spec: `apps/web/e2e/fixtures-w2-hunt.e2e.ts`, test `"10-bit HDR HEVC — import
  behavior + real export (no crash)"`. Requires the real Chrome channel (see
  `apps/web/playwright.fixtures-w2.config.ts`) — Playwright's bundled
  Chromium has no H.264/HEVC WebCodecs decode.
- Prior finding (bug-purge-w2, `apps/web/docs/campaigns/bug-purge-w2.md` line
  ~132): import/edit/export all succeed with no crash; the exported MP4 is
  tagged/rendered as ordinary bt709 SDR with no tonemap step. This task
  re-confirms and traces the exact mechanism.

## Traced decode → composite → encode path

1. `SceneExporter.export()` (`apps/web/src/services/renderer/scene-exporter.ts:133-145`)
   loops frames and calls `this.renderer.render({ node: rootNode, time })`,
   then reads pixels straight off `this.renderer.canvas` via mediabunny's
   `CanvasSource` (`videoSource.add(time, 1/fps)`). It never touches a
   `VideoFrame` or color space value directly — it only ever sees the already-
   composited 2D canvas.
2. `CanvasRenderer` (`apps/web/src/services/renderer/canvas-renderer.ts`)
   creates its backing store via `getContext2D()`
   (`apps/web/src/services/renderer/canvas-utils.ts:31-40`), which calls
   `canvas.getContext("2d")` with **no `colorSpace` option** — this defaults
   to `"srgb"`. **Note: `CanvasRenderer` is shared with the live preview path**
   (GitNexus `impact({target:"CanvasRenderer", direction:"upstream"})` →
   CRITICAL, 125 impacted symbols across `useEditorActions`/`Editor`/Preview —
   confirming it is not export-exclusive and out of bounds for an export-only
   fix per this task's constraints).
3. Per-clip frames are supplied to `CanvasRenderer` by `VideoNode.render()`
   (`apps/web/src/services/renderer/nodes/video-node.ts:91-99`, **sibling-
   owned, not touched**), which calls `videoCache.getFrameAt(...)`
   (`apps/web/src/services/video-cache/service.ts`, **sibling-owned, not
   touched**) and receives back a mediabunny `WrappedCanvas` — i.e. **an
   already-rendered `HTMLCanvasElement`/`OffscreenCanvas`**, not a
   `VideoFrame`.
4. `videoCache`'s decode path (`service.ts:657-669`) constructs a mediabunny
   `CanvasSink` directly on the `InputVideoTrack` — `new CanvasSink(videoTrack,
   { poolSize, fit: "contain", ...outputSize, decoderOptions })`. `CanvasSink`
   is the mediabunny primitive that internally does WebCodecs decode → yields
   `WrappedCanvas`.
5. **This is the actual conversion boundary**, and it lives entirely inside
   the `mediabunny` npm package (v1.50.7, `node_modules/mediabunny/src/media-
   sink.ts`), not in any first-party file:
   `CanvasSink._videoSampleToWrappedCanvas()` (`media-sink.ts:1954-2011`) does
   `canvas.getContext('2d', { alpha })` (again no `colorSpace` — defaults to
   `srgb`) then calls `sample.drawWithFit(context, {...})`
   (`VideoSample.drawWithFit`, `sample.ts:1235-1305`), which resolves to a
   plain `context.drawImage(source, ...)` where `source` is the underlying
   `VideoFrame`/`CanvasImageSource` (`sample.ts:1202,1217`).
6. **`context.drawImage(videoFrameOrSample)` onto a `colorSpace:"srgb"` 2D
   context is where Chrome performs its native PQ→SDR color management.**
   Per the WHATWG Canvas/WebCodecs HDR color-management model, the browser is
   required to convert the `VideoFrame`'s tagged color space (here:
   primaries=bt2020, transfer=smpte2084/PQ, matrix=bt2020-ncl) into the
   destination canvas's `srgb` color space — but the specific HDR→SDR
   luminance mapping used is **implementation-defined**, not something any
   application code (ours or mediabunny's) can select, configure, or inspect.
   By the time `_videoSampleToWrappedCanvas` returns, the `WrappedCanvas` its
   caller (`videoCache`, then `VideoNode`, then `CanvasRenderer`, then finally
   `SceneExporter`) receives is **already 8-bit SDR/srgb — the HDR pixel data
   is gone**, no matter how far upstream (mediabunny) or downstream
   (`scene-exporter.ts`) you intervene from that point on.
7. `SceneExporter`'s `CanvasSource` (mediabunny `media-source.ts`) has no
   `colorSpace`/HDR options either — it just encodes whatever 8-bit sRGB
   pixels are already in the canvas as H.264 (`avc`), which is bt709-range by
   convention. **This confirms the bug is not a metadata-mistagging issue**:
   the bt709 tag on the exported MP4 is *accurate* for the SDR pixel data
   that is actually in the canvas by then. The defect is entirely upstream,
   at step 6.

## Empirical characterization (Q2) — partial: reference conversions computed,
## live-Chrome pixel capture blocked by shared-machine build contention

**What was attempted:** run the actual HDR export through
`fixtures-w2-hunt.e2e.ts`'s "10-bit HDR HEVC" test via real Chrome
(`channel:"chrome"`, the only browser build in this environment with H.264/
HEVC WebCodecs decode — Playwright's bundled Chromium has none), pull the
export bytes out of the E2E bridge, and diff a frame against independently-
computed PQ→BT.709 reference conversions.

**What blocked it:** the test's `webServer` requires a production
`next build` (`build:e2e:real`). This machine had **8+ concurrent
`next build`/`next dev` processes** running from other active worktree
sessions at the time (per this repo's own multi-session-git-coordination
convention: several agents share this machine concurrently). Load average
climbed from 16 to 22 over the attempt; the build's own compiler process sat
at **0% CPU for 28+ minutes with zero incremental output** (`.next/server/`
stayed empty) — a genuine starvation stall, not "just slow" (a first full
Turbopack build of this app normally completes; it never got past
"Creating an optimized production build ..."). Continuing to wait, or to
retry, would only add another idle stalled build to the contention rather
than resolve it. The stalled processes were killed to free the shared
machine rather than left running.

**What was still established with real evidence** (no browser needed for
this part — it's ground-truth color science applied directly to the
fixture's raw decoded pixels via `ffmpeg -pix_fmt rgb48be`, independent of
any browser/Chrome behavior):

- The source fixture's PQ/BT.2020 code values were extracted losslessly
  (16-bit, `ffprobe`-confirmed `rgb48be(pc, gbr/bt2020/smpte2084)`) and run
  through a from-scratch SMPTE ST 2084 inverse-EOTF + BT.2020→BT.709
  primaries matrix + John Hable "Uncharted 2" filmic tonemap (npl=100) —
  the same public-domain algorithm `ffmpeg`'s own `tonemap=hable` filter
  implements. (This ffmpeg build lacks `libzimg`/`zscale`, so the reference
  was computed directly in Python rather than via the usual
  `zscale=t=linear,tonemap=hable,zscale=t=bt709` chain — same math, verified
  against known PQ reference points: 100 nits → code value 0.5081, 203 nits
  (BT.2408 SDR reference white) → 0.5807 — both match the standard published
  figures, and the BT.2020→BT.709 matrix used conserves white point
  (`M·[1,1,1]ᵀ ≈ [1,1,1]ᵀ`) to 4 decimal places.)
- A **hard-clip-no-tonemap** variant (correct EOTF/gamut conversion, but
  highlights above 1.0 clipped rather than rolled off) and a **zero-color-
  management** baseline (PQ code values byte-truncated and treated as
  already-sRGB, i.e. what a total pass-through would look like) were
  computed from the same source pixels for comparison.
- **Numeric proof the defect is real and large, independent of exactly
  which SDR-mapping variant Chrome's internals use**: the fixture's
  reference gray test-patch (raw PQ code value ≈0.495) correctly decodes via
  PQ EOTF to ≈87.7 nits (a deliberate near-SDR-white test value). If that
  same code value were instead decoded with an sRGB/BT.709 EOTF (i.e. no PQ
  awareness at all), it resolves to ≈20.9 nits-equivalent — a **~4x
  photometric error**, which is the kind of magnitude a "washed-out/crushed"
  visual complaint is consistent with. This nails down that *some* transfer-
  function-aware conversion must be happening for the reported symptom to
  be merely "washed out and crushed" rather than "the entire midtone range
  is catastrophically dark" — i.e. Chrome's `drawImage` almost certainly
  *is* doing real PQ-aware color management (per spec, it's required to),
  just not a perceptually-tuned filmic tonemap, so the visible defect is
  most consistent with the **hard-clip / no-tonemap-curve** hypothesis
  (highlights compressed/clipped harshly, no filmic roll-off) rather than
  "zero conversion." This is inference from the spec + the math, not a
  confirmed browser pixel capture — flagged as the residual open item below.

**Residual open item:** confirming Chrome's *exact* SDR-mapping algorithm
(hard-clip vs. some other implementation-defined curve) still requires the
live-Chrome pixel capture that build contention blocked. This does **not**
change the fix-scope conclusion below — it would only refine the "how wrong"
detail, not the "contained vs. architectural" verdict, which rests on the
source-code trace (steps 1-7 above), independent of exactly which flavor of
SDR mapping Chrome performs.

## Why a contained fix in `scene-exporter.ts` is not viable

The task's owned-file scope (`scene-exporter.ts` + a new tonemap helper under
`services/renderer/`) only ever sees frames *after* step 6 above — i.e.
after Chrome's browser-native, unconfigurable HDR→SDR conversion has already
run and thrown away the HDR signal. Two theoretically-available insertion
points were considered and rejected:

- **Inside `SceneExporter.export()`'s per-frame loop**, after
  `this.renderer.render(...)`, before `videoSource.add(...)`: this is
  GitNexus-confirmed LOW risk and fully contained
  (`impact({target:"SceneExporter.export", direction:"upstream"})` → 6
  impacted symbols, 2 direct callers, 0 processes, LOW risk) — but the only
  data available here is the final **composited** (all layers/watermark
  already alpha-blended) 8-bit sRGB canvas. Any "tonemap" applied at this
  point would be a cosmetic curve/LUT on already-clipped, already-desaturated
  bytes — it cannot recover highlight detail Chrome already hard-clipped in
  step 6, cannot distinguish which pixels came from the HDR clip vs. an SDR
  text/image overlay composited on top, and is not a real HDR tonemap by any
  meaningful definition. Implementing this would misrepresent a color-grade
  hack as a fix for the reported defect.
- **Inside `CanvasRenderer`**: rejected outright — GitNexus impact is
  CRITICAL (shared with the live preview path; this task is export-only
  scope per the objective, and `canvas-renderer.ts` isn't in the owned-file
  list).

There is no point *before* step 6 that is reachable without editing
`services/video-cache/service.ts` (owns the `CanvasSink` construction) or
`services/renderer/nodes/video-node.ts` (both explicitly off-limits for this
task).

## Scoped fix proposal (for the sibling owner / a follow-up task)

mediabunny exposes the pieces needed, just not through `CanvasSink`:

1. `InputVideoTrack.hasHighDynamicRange()` and `.getColorSpace()`
   (`node_modules/mediabunny/src/input-track.ts:711-719`) — public API,
   already returns exactly the `primaries==="bt2020" || transfer==="pq" ||
   transfer==="hlg" || matrix==="bt2020-ncl"` check needed to gate this.
2. `VideoSampleSink` (lower-level than `CanvasSink`, already used elsewhere
   in this codebase for thumbnails — see
   `apps/web/src/lib/media/processing.ts:135-153`) yields raw `VideoSample`s
   whose `.colorSpace` is preserved and whose `.draw()` is the same
   `drawImage`-based call `CanvasSink` uses internally. Swapping `video-
   cache/service.ts`'s `CanvasSink` for a `VideoSampleSink` when
   `hasHighDynamicRange()` is true would let it intercept the sample *before*
   the lossy `drawImage` call.
3. The actual tonemap would need a manual GPU (WebGL/WebGPU) or CPU pass
   applying: PQ inverse-EOTF → BT.2020→BT.709 primaries matrix → a filmic
   tonemap curve (e.g. Hable, npl=100) → sRGB OETF — writing the result into
   the canvas mediabunny's caller expects, in place of the single
   `sample.drawWithFit()` call. mediabunny's public API has **no built-in
   tonemap option on either sink** (`CanvasSinkOptions` in `media-
   sink.ts:1774+` only exposes `alpha`/`width`/`height`/`fit`/`rotation`/
   `poolSize`/`decoderOptions` — no `colorSpace` or tonemap knob), so this
   is genuinely a from-scratch implementation, not a config flag.
4. HDR detection would also need to be threaded from ingest
   (`lib/media/normalize-media.ts`'s `ProbeResult`, which currently has no
   HDR field at all) through asset metadata and into `scene-builder.ts`
   (confirmed: `SceneBuilder`'s `new VideoNode({ mediaId: mediaAsset.id, ...
   })` around `scene-builder.ts:211-212` passes only `mediaId`/geometry —
   `mediaMap`/`mediaAsset` carries no color-space or HDR field anywhere in
   this path) so `video-node.ts`/`video-cache` know when to take the HDR
   path — a genuine cross-cutting change touching ingest, asset metadata
   shape, scene-builder, and video-cache, not a one-file patch.
5. Related, out-of-scope-for-this-task observation: the exact same
   `drawImage`-based flattening (via `VideoSample.draw`, same root cause)
   also runs in `lib/media/processing.ts`'s thumbnail generator
   (`decodeAllFrames` → `frame.draw(context, ...)`), so HDR thumbnails are
   presumably also silently SDR-crushed. Not verified here (export-only
   scope) but worth a queue row if confirmed.
