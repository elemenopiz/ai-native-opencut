## 🚫 BLOCKED-1 — Transitions render blank frames (CRITICAL, live)

- **File:** `apps/web/src/services/renderer/nodes/transition-node.ts:88-127`
  (`renderSourceFrame`)
- **Wired in at:** `apps/web/src/services/renderer/scene-builder.ts:289`
  (`new TransitionNode(...)`) — so this affects **every preview and export**.

**Defect.** `renderSourceFrame` creates a fresh transparent `OffscreenCanvas`,
computes the transform/opacity for the source clip, sets `ctx.globalAlpha`, and
then **returns the canvas without ever drawing the clip's frame onto it.** It
never calls `videoCache.getFrameAt(...)` (as `VideoNode` does) nor loads the
image source (as `ImageNode` does), and never reads the declared-but-unused
params `mediaMap` / `mediaIdA` / `mediaIdB`. Every transition therefore blends
two blank canvases — crossfades/wipes show nothing instead of the outgoing and
incoming clips.

**Why blocked.** The remedy is **completing an unfinished feature**, not a patch:
`renderSourceFrame` must asynchronously fetch each source frame (video via
`videoCache.getFrameAt`, image via an image load using `mediaMap` + `mediaIdA/B`),
apply the resolved transform, and `drawImage` — which also means making the
method `async` and awaiting both sources in `render()`. Correctness depends on
the `videoCache` API and transform math, and it can only be verified by rendering
and eyeballing output (no headless assertion). Mirror `VideoNode` / `ImageNode`.

**Suggested approach.** Extract the frame-fetch+transform+draw used by
`VideoNode`/`ImageNode` into a shared helper and reuse it for both transition
sources; add a visual smoke test (render a 2-clip crossfade, sample a mid-
transition pixel).

## 🚫 BLOCKED-2 — Auto-review corrections bypass the whole-reel budget (HIGH)

- **File:** `apps/web/src/lib/director/agent.ts` — `autoReviewSlot` (~1003-1050),
  called from `finalize()` (~1402).

**Defect.** `autoReviewSlot` gates its corrective `reroll` / `remix` only on the
**flat per-action approval threshold** (`needsApproval(est, threshold)`), and
calls the `DirectorApi` verbs directly — bypassing the tool-execution loop
(`agent.ts:1481-1570`) that runs `evaluateBudgetGate()` and, on success,
`director.recordSpend({ usd: budget.costUsd })`. Under an active **whole-reel
budget**, every auto-review correction (reroll-with-delta, remix-with-anchor,
remix-for-continuity):
1. is **not** checked against the remaining reel cap, and
2. **never advances `spend.spentUsd`**,
so the budget panel undercounts and later same-turn gate decisions operate on a
stale (too-generous) remaining balance.

**Why blocked.** This is money accounting in a recently-built feature. The
correct fix routes auto-review through the same `evaluateBudgetGate` +
`recordSpend` pipeline the interactive loop uses, recording the **canonical**
cost. Recording a *guessed* amount (min/max/mid of the estimate) would make the
tally wrong in a new way. Needs budget-accounting review + verification.

**Note.** The related interactive-loop gap — `remix` being entirely ungated —
**was fixed** (commit `fix: gate director 'remix' against budget/approval like
reroll`). This item is only the auto-review path.

## 🚫 BLOCKED-3 — Same-track ripple drag drops the ripple shift (HIGH, live)

- **File:** `apps/web/src/lib/commands/timeline/element/move-elements.ts:104-111`
  (`MoveElementCommand.execute`, same-track branch)
- **Reached from:** `apps/web/src/hooks/timeline/element/use-element-interaction.ts:468`
  (`moveElement({ …, rippleEnabled })` on same-track drops).

**Defect.** When a move is within the same track, `execute()` just replaces the
moved element and returns — it never calls `rippleShiftElements` on the sibling
elements, unlike the cross-track branch (lines 113-124). So a ripple-mode drag
inside one track silently does not ripple, even though `rippleEnabled` is passed.

**Why blocked.** A same-track ripple move is a **reorder**, not a simple
insert/delete: it must close the gap left at the element's old position **and**
open a gap at its new position (with the drop time computed against the shifting
layout). The semantics are ambiguous, there is no spec or test, and this is core
timeline editing (HIGH blast radius). A speculative fix could corrupt timelines;
it needs a product decision on the intended behavior + visual verification.

## 🚫 BLOCKED-4 — nest-clips / unnest-clips report success but do nothing (HIGH)

- **File:** `apps/web/src/hooks/actions/use-editor-actions.ts:603-625`

**Defect.** Both action handlers validate the selection count and then call
`toast.success("Clips nested into compound clip")` / the unnest equivalent —
with **no call into `editor.timeline` or any command**. The timeline is
unchanged; the user is told it worked. (Related to the deferred dead
`NestClipsCommand`, which is itself buggy — see Deferred below.)

**Why blocked.** Needs a product decision: either (a) wire the actions to a
correct compound-clip command (the existing `NestClipsCommand` is buggy and
must be fixed first), (b) show an honest "not yet available" message, or (c)
remove the actions from the registry. Not a mechanical fix.

## 🚫 BLOCKED-5 — custom shortcut recorder encodes combos differently than the matcher (HIGH)

- **Files:** recorder `apps/web/src/app/shortcuts/page.tsx:134-154` vs. matcher
  `apps/web/src/stores/keybindings-store.ts:178-225`.

**Defect.** The recorder builds the combo string as modifiers in order
`ctrl, shift, alt` using raw `e.key.toLowerCase()`. The real keydown matcher
(`getActiveModifier`/`getPressedKey`) builds modifiers in order `ctrl, alt,
shift` and normalizes special keys (space, arrows, escape, tab, home/end,
delete/backspace) to fixed tokens. So a recorded `alt+shift+x` is stored as
`shift+alt+x` and never matches the canonical `alt+shift+x`; space/arrow/escape
shortcuts store the wrong token. The just-recorded custom shortcut silently
never fires.

**Why blocked.** The correct fix is to make the recorder reuse the canonical
`getActiveModifier`/`getPressedKey` encoding from `keybindings-store.ts` instead
of duplicating it. That touches shared shortcut-encoding logic used across all
custom bindings and needs verification against the full matcher (and possibly a
migration for already-saved malformed bindings) — too broad to land blindly.

## 🚫 BLOCKED-6 — split-right never ripple-closes its gap (MED)

- **Files:** `apps/web/src/hooks/actions/use-editor-actions.ts:201-222` +
  `apps/web/src/lib/commands/timeline/element/split-elements.ts:84-116`.

**Defect.** split-left passes `rippleEnabled` into `splitElements`; the symmetric
split-right omits it (defaults `false`). Worse, `SplitElementsCommand` only
implements the ripple-shift for the `retainSide === "right"` path — the
`retainSide === "left"` path (used by split-right) never checks `rippleEnabled`
at all. So with Ripple Editing on, split-right leaves a gap the mirror op closes.

**Why blocked.** Same family as BLOCKED-3 (ripple semantics): the ripple-shift
must be implemented for the left-retain path with the correct gap math, which is
core timeline editing needing a spec + visual verification.

## Deferred — dead code / unwired features (latent, zero blast radius today)

misbehave until wired up. Left as-is; fix if/when the feature is activated.

  No caller anywhere. Fix: append the compound to a single track and derive its
  type.
- **`apps/web/src/hooks/use-studio-generation.ts:63`** — `cancelRef` is checked
  in the poll loop but never set to `true` (no `cancel()` is exported/wired), so
  the cancellation path is unreachable. Half-wired feature, not a
  wrong-behavior defect. Fix: expose and wire a `cancel()` action.
